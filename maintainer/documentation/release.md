# Выпуск документации и связь с 1С

У комплекта есть версия документации, версия приложения и контрольные суммы. Эти данные
должны позволять связать решение проверяющего с конкретным файлом, а не с меняющимся сайтом.

## Подготовить артефакты

1. Обновите `project.json`, метаданные страниц и `CHANGELOG.md`.
2. Выполните `npm.cmd run check` и осмотрите сайт.
3. Выполните `npm.cmd run release:manifest`.
4. В `exports/` проверьте три объединённых Markdown-файла, `release-manifest.json`
   и `SHA256SUMS.txt`. Манифест содержит SHA-256 каждого исходника и готового руководства.

Артефакты собираются из страниц каждого руководства в порядке навигации. Относительные
ссылки пересчитываются к каталогу `exports/`, изображения сохраняют связь с `docs/public/`.
Это самостоятельные исходники для чтения и последующего оформления, а не финальная вёрстка DOCX/PDF.
Экспорт Word и копии для курсового отчёта будут отдельной работой.

## Привязать к редакции 1С

Для локальной демонстрации сохраните готовый Markdown-файл неизменяемой копией,
в карточке редакции укажите ссылку на него и SHA-256 из манифеста. Для размещённого репозитория
используйте ссылку на конкретный коммит и путь к файлу в
[репозитории документации](https://github.com/DmiBear/docrelease).

Выпуск трёх руководств — три карточки документов и три редакции. Проверяющий читает файлы
и оформляет решения по их передачам. Руководитель включает согласованные редакции в план,
проверяет готовность и проводит выпуск. Сборка сайта сама по себе не согласует тексты.

Если зафиксирован Git-коммит, не включайте в этот же коммит манифест с хэшем самого себя:
получится циклическая зависимость. Скрипт создаёт артефакт в игнорируемом `exports/` и записывает
имеющийся HEAD, либо `null`, если репозиторий ещё без коммитов. Содержимое идентифицируется SHA-256
готового файла независимо от наличия коммита.
