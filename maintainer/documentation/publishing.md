# Подготовка GitHub и Pages

Локальный проект готовится к размещению, но создание удалённого репозитория, push и
публичная публикация выполняются отдельно владельцем. В этом комплекте нет токенов и готового удалённого адреса.

## Первый push

Проверьте `git status --short` и список добавляемых файлов. В Git не должны попасть
`.local`, `node_modules`, `exports`, `.dt`, `1Cv8.1CD`, ключи и журналы. Сначала выполните
`npm.cmd run check`. Создайте на GitHub пустой репозиторий без предварительных файлов.

В локальном репозитории настройте свои имя и email Git, создайте первый коммит и добавьте
полученный от GitHub адрес как `origin`. Если удалённый репозиторий уже содержит историю,
сначала изучите её; не используйте принудительную отправку для перезаписи.

```powershell
git add .
git commit -m "Add DocRelease application sources and documentation"
git remote add origin <адрес-созданного-репозитория>
git push -u origin main
```

`<адрес-созданного-репозитория>` заменяется настоящим адресом. Команды здесь являются
инструкцией; наличие текста не означает, что отправка была выполнена.

## Проверка в GitHub Actions

Workflow `Documentation checks` запускает `npm ci --ignore-scripts`, проверки и сборку
на push и pull request. Он не запускает Windows-платформу 1С. Проверка сайта не заменяет TC-01–TC-17.

## Публикация Pages

В настройках репозитория выберите Pages из GitHub Actions, затем вручную запустите
workflow **Publish documentation** для нужной ветки. Он соберёт сайт с базовым путём
имени репозитория и опубликует артефакт Pages. Для репозитория вида `owner.github.io`
используется корень `/`. Учёт особого домена потребует отдельной настройки.

Проверьте полученный URL, три руководства, поиск, изображения и ссылки из подпапки.
Не включайте публичный адрес в документы до фактического появления сайта.
Перед публичным размещением владелец выбирает условия распространения исходников и материалов;
лицензия в этом комплекте не назначена автоматически.
